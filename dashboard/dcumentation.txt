PART 1 — WHAT THIS PROJECT IS
--------------------------------------------------------------------------------

The Probabilistic Smart Home Decision Network (BDN) is an end-to-end machine
learning system that watches raw smart-home sensor event logs and, every 5
seconds, (a) infers what the residents are probably doing and (b) decides what
the home should do about it.

It is built as a 26-node Bayesian / Decision Network over three public CASAS
smart-home datasets (Aruba, Cairo, Milan):

  * PROBABILISTIC INFERENCE: an 18-evidence-node → 6-behavioral-node Bayesian
    Network learns how sensor patterns relate to resident states. Given the
    current 5-second window of sensor evidence, it computes exact posterior
    probabilities for Home_Occupancy, Resident_Activity, Resident_Sleep,
    Leaving_Home, Returning_Home and Unusual_Activity.

  * DECISION MAKING: a decision node (Smart_Home_Action) with 5 candidate
    actions (No_Action, Monitor, Notify_Resident, Silent_Alert, Local_Alert)
    and a utility node (Homeowner_Utility). The system selects the action that
    maximizes Expected Utility given the posterior state of the home (MEU).

The deliverables are: a reproducible pipeline (main.py, 10 steps), a trained
model (outputs/models/bayesian_network.pkl), a full evaluation report
(outputs/FINAL_RESULTS.md) with metrics and 10 figures, a test suite, and a
live web dashboard (dashboard/) that replays the test set and streams real
inference results to the browser in real time.

PART 2 — DATASET: WHAT WE USE AND WHY
--------------------------------------------------------------------------------

2.1 The data
    Three CASAS smart-home datasets, each a raw event log with 4 columns
    (date, time, location, event):

      Home  | Raw Events  | Date range              | Locations | Event types
      ------+-------------+-------------------------+-----------+----------------
      Aruba | 1,602,821   | 2010-11-04 → 2011-06-11 | 10        | ON, OFF, OPEN, CLOSE
      Cairo |   647,487   | 2009-06-10 → 2009-08-05 |  8        | ON, OFF only
      Milan |   421,392   | 2009-10-16 → 2010-01-06 |  9        | ON, OFF, OPEN, CLOSE

      Total: 2,671,700 raw events, 11 unique locations across homes.

    Locations are rooms/sensors: Bedroom, Bathroom, Kitchen, LivingRoom,
    DiningRoom, GuestRoom, LoungeChair, OtherRoom, OutsideDoor, WorkArea, Hall.
    Events are binary sensor transitions: ON/OFF (motion/contact sensors) and
    OPEN/CLOSE (door contact sensors).

    WHY CASAS: (1) It is the de-facto public benchmark for smart-home activity
    research, so results are comparable with the literature. (2) The three
    homes share a schema but differ in sensor sets and layout, which lets us
    test cross-home generalization honestly. (3) Months of continuous real
    data per home gives millions of windows for reliable CPT estimation.
    (4) Fully public and license-free for academic use.

    WHY THESE THREE HOMES: they form a natural difficulty gradient — Aruba is
    the richest (10 locations, 4 event types), Milan is mid-size, and Cairo is
    the sparsest (8 locations, motion-only ON/OFF) and therefore the stress
    test for missing-sensor handling (Cairo has no Bathroom/DiningRoom/
    LoungeChair sensors and no OPEN/CLOSE door events at all).

2.2 Project contract on missing data (defended)
    A sensor that does not exist in a home is encoded as the categorical state
    "Unavailable" — NEVER as zero. This preserves the semantic difference
    between "the sensor exists and observed nothing" (None) and "the sensor
    does not exist" (Unavailable). Cairo's ON/OFF outside door is likewise NOT
    converted to OPEN/CLOSE; instead its contact activity is counted through
    Total_Contact_Events and the two door-open/close evidence nodes are marked
    Unavailable for Cairo. No environmental variables (temperature, humidity,
    electricity, HVAC, camera) are fabricated — CASAS simply does not contain
    them.

PART 3 — METHODOLOGY AND WHY WE CHOSE IT
--------------------------------------------------------------------------------

3.1 Windowing (5-second tumbling windows)
    Raw events are binned into non-overlapping 5-second windows
    (window_start = timestamp.floor("5s")). WHY: (a) Raw events are extremely
    sparse — instantaneous ON/OFF transitions with minutes-long gaps — while a
    Bayesian network needs a fixed set of observations per sample. (b) A 5 s
    granularity is short enough to localize behaviour (a door event, a burst
    of kitchen activity) yet long enough to aggregate multiple sensor
    transitions into a meaningful activity count. (c) Tumbling (non-overlap-
    ping) windows prevent leakage between train/test samples and keep the
    sample count tractable (~1.08 M windows from 2.67 M events).

3.2 Discrete Bayesian Network (chosen model)
    The behavioral layer is modeled as a discrete BN with a hand-designed,
    semantically meaningful DAG (39 edges, max parent set 4). WHY a discrete
    BN: (a) Our evidence is naturally categorical (activity counts binned to
    None/Low/High, time-of-day buckets), and discretized BNs train reliably
    with millions of samples. (b) BNs give interpretable CPTs and exact
    posterior marginals — every probability the dashboard shows is explainable
    — unlike black-box sequence models. (c) Exact inference (Variable
    Elimination) is fast (~1 ms/query measured), enabling a real-time
    dashboard. (d) The DAG itself documents domain assumptions (e.g., door
    activity feeds Leaving_Home; night-time + bedroom activity feeds
    Resident_Sleep), which a generic neural net would not.

    WHY BDeu (Bayesian Dirichlet equivalent uniform, ESS=5) smoothing: with 26
    categorical nodes and parent sets up to size 4, some parent configurations
    are rare. BDeu with a small equivalent sample size regularizes CPTs toward
    uniform priors in sparse cells, guaranteeing every conditional
    distribution is valid (no zero-probability explosions) without distorting
    well-observed cells. ESS=5 is the pgmpy-typical weakly-informative choice.

    WHY Variable Elimination (exact) rather than sampling: the network is
    small (26 nodes, 24 probabilistic), so exact marginals cost ~1 ms and are
    deterministic — better than approximate Gibbs/likelihood-weighting for a
    live dashboard where latency and reproducibility matter.

3.3 Decision layer (Influence Diagram / MEU)
    The decision node Smart_Home_Action has 5 actions; the utility node
    Homeowner_Utility is defined over 6 mutually exclusive situational states
    built from three binary facets: Unusual? × Occupied? × Sleeping?:
      Normal_Awake, Normal_Sleeping, Normal_Empty,
      Unusual_Occupied_Awake, Unusual_Occupied_Sleeping, Unusual_Empty.
    EU(action) = Σ_state P(state|evidence) · U(action, state); the argmax is
    executed. WHY MEU: it makes the safety/disruption trade-off explicit and
    auditable (utility_table.csv), it gracefully interpolates between states
    when the network is uncertain, and it yields a principled graded response
    (No_Action → Monitor → Notify → Silent_Alert → Local_Alert) instead of
    brittle hard thresholds.

    WHY 6 states instead of a full 2×2×2=8 grid: Leaving/Returning are
    transitory events, not persistent situations, so the utility model uses
    only the three persistent facets. WHY the extreme negative utilities
    (e.g., No_Action in Unusual_Empty = −120): they encode the deliberate
    design stance that ignoring a possible hazard is far costlier than a
    nuisance alert — the classic asymmetric-loss argument for alarm systems.
    The utility numbers are project-defined assumptions (documented in
    outputs/metrics/utility_table.csv) and would ideally be elicited from
    real homeowner preference studies — stated openly as a limitation.

3.4 Weak labels (honest supervision)
    The 6 behavioral variables are generated by transparent, documented
    heuristic rules on the event stream (e.g., Leaving_Home = door activity
    followed by ≥10 min of silence; Resident_Sleep = night + occupied + no
    kitchen/living activity + low overall activity; Unusual_Activity = night
    door events / high non-bedroom night activity / activity while empty).
    WHY: CASAS ships no behavioral ground truth, and unsupervised anomaly
    detection would give us nothing to evaluate against. Weak labels provide
    (a) targets for training the BN and (b) a comparison standard for
    evaluation. We explicitly report that metrics measure MAP-vs-weak-label
    agreement, not verified ground truth, and that Unusual_Activity is a
    behavioral-deviation signal, NOT intrusion detection.

3.5 Chronological splitting (70/15/15, no shuffling)
    WHY: shuffling would leak future information into training (adjacent
    windows are highly correlated), inflating metrics. A chronological split
    per home evaluates true forecasting-like performance. Validation guides
    nothing that touches the test set; all thresholds and CPTs are fitted on
    the training partition only.

3.6 Baseline and evaluation protocol
    A deterministic rule-based baseline (Unusual→Local_Alert; else
    Returning/Leaving→Monitor; else No_Action) is evaluated with the same
    realized-utility function, so the Bayesian decision layer's added value is
    measured, not assumed. Behavioral metrics: accuracy, weighted F1, macro F1
    per variable. Decision metrics: mean/median/total utility, false-alert
    rate, unusual-detection rate, action distribution. Latency is measured on
    real hardware over 3,000 queries. Cross-home experiments (Aruba→Aruba,
    Aruba→Milan, Aruba+Milan→Cairo) train on one sensor subset and evaluate on
    a different home using only the target home's available evidence.

PART 4 — IMPLEMENTATION LIBRARIES
--------------------------------------------------------------------------------

4.1 Core scientific stack (root requirements.txt)
    pandas (3.0.6)      — CSV I/O, crosstab/window aggregation, datetime floors,
                          chronological splitting. Chosen as the standard
                          tabular engine; windows are built with vectorized
                          groupby/crosstab, not Python loops.
    numpy (2.5.3)       — array math, np.select for rule engines.
    pgmpy (1.1.2)       — THE probabilistic engine. DiscreteBayesianNetwork for
                          the DAG, DiscreteBayesianEstimator (BDeu) for CPTs,
                          VariableElimination for exact inference. Chosen as
                          the most complete open-source Python BN library with
                          a clean estimator/inference API.
    networkx (3.7)      — DAG representation and acyclicity validation for the
                          26-node structure (the dashboard graph itself uses a
                          deterministic pipeline-stage layout, not a random
                          spring embedding).
    matplotlib/seaborn  — the 10 evaluation figures (Agg backend).
    scikit-learn        — accuracy/F1/confusion-matrix metrics.
    scipy               — statistical support used by the stack.
    pytest              — 10 unit tests (tests/test_pipeline.py).

4.2 Dashboard stack (not in requirements.txt; installed by run_dashboard.sh)
    FastAPI (0.142.2)   — async web framework; serves the SPA and REST API.
    Uvicorn (0.54.0)    — ASGI server (uvicorn[standard] extras for websockets).
    websockets (17.2)   — the WS implementation Uvicorn needs for /ws.
    D3.js v7 (CDN)      — frontend network-graph visualization (zoom/pan,
                          curved edges, tooltips).
    Inter + JetBrains Mono (Google Fonts) — dashboard typography.

    WHY FastAPI rather than Flask: native async (needed for the concurrent
    WebSocket playback loop and many simultaneous clients), built-in
    validation, and first-class WebSocket support.

4.3 Reproducibility
    Python 3.12, fixed random seed 42, all versions pinned in
    outputs/metrics/run_config.json written at pipeline run time.

PART 5 — ARCHITECTURE (26 NODES, 39 EDGES)
--------------------------------------------------------------------------------

  Evidence (18)                Behavioral (6)          Decision (1)   Utility (1)
  ─────────────────────        ─────────────────       ────────────   ───────────
  Room activity ×11     →      Home_Occupancy     →    Smart_Home     Homeowner
   (Bedroom, Bathroom,         Resident_Activity       _Action        _Utility
   DiningRoom, GuestRoom,      Resident_Sleep
   Kitchen, LivingRoom,        Leaving_Home
   LoungeChair, OtherRoom,     Returning_Home
   OutsideDoor, WorkArea,      Unusual_Activity
   Hall)
  Door events ×2        →            ↑
   (OutsideDoor_Open/Close)    (behavioral layer)
  Temporal ×3
   (Time_Of_Day, Day_Of_Week,
   Is_Night)
  Aggregates ×2
   (Total_Activity,
   Total_Contact_Events)

  Total: 18 + 6 + 1 + 1 = 26 nodes; 39 directed edges; acyclic (validated);
  24 CPTs learned; max parent set size 4.

  Key structural assumptions (defended):
  * Time_Of_Day → Is_Night, Day_Of_Week → Time_Of_Day: calendar causality.
  * Room activity → Total_Activity; door events → Total_Contact_Events:
    aggregates are deterministic summaries of their parts.
  * Total_Activity + OutsideDoor_Activity → Home_Occupancy: occupancy is the
    central hidden variable driven by aggregate indoor and door evidence.
  * Home_Occupancy → Resident_Activity/Resident_Sleep/Leaving/Returning: you
    cannot be active or asleep in an empty house; transitions need occupancy.
  * Resident_Activity → the 7 secondary room activities: rooms are visited as
    a function of overall resident activity level.
  * Is_Night + Bedroom_Activity → Resident_Sleep: the sleep heuristic's direct
    drivers.

PART 6 — RESULTS SUMMARY (from outputs/FINAL_RESULTS.md)
--------------------------------------------------------------------------------

  Modeling dataset: 1,078,797 windows (Aruba 656,811 / Cairo 226,259 /
  Milan 195,727). Split: train 755,156 / validation 161,820 / test 161,821.

  Behavioral inference (test subset n=3,000), MAP vs weak labels:
    Home_Occupancy   99.97% acc   (macro-F1 0.4999 — imbalanced classes)
    Resident_Activity 99.97% acc  (macro-F1 0.7499)
    Resident_Sleep    98.10% acc  (macro-F1 0.8600)
    Leaving_Home      99.97% acc
    Returning_Home    99.33% acc
    Unusual_Activity  99.87% acc  (macro-F1 0.8568)

  Decision metrics (n=3,000):
    Mean utility: BDN 10.173 vs rule baseline 10.173; false-alert rate 0.0%
    for both. The BDN uses a graded response (No_Action 99.57%,
    Notify_Resident 0.27%, Silent_Alert 0.17%) while the baseline is binary
    (No_Action 99.03%, Monitor 0.67%, Local_Alert 0.30%). Interpretation: the
    BDN matches the baseline's average utility while producing proportionate,
    less disruptive responses, and its higher utility std (2.796 vs 1.713)
    reflects that graded behavior.

  Inference latency (3,000 real queries): mean 0.984 ms, p95 1.170 ms,
  p99 2.115 ms, max 3.175 ms — comfortably real-time.

  Cross-home generalization: occupancy/activity accuracy 100% and sleep
  accuracy 96–98% when transferring Aruba→Milan and Aruba+Milan→Cairo with
  only the target home's sensors as evidence.

PART 8 — DEFENSE OF CHOICES (QUICK-REFERENCE MATRIX)
--------------------------------------------------------------------------------

  Choice                    | Why (one line)
  --------------------------+--------------------------------------------------
  CASAS datasets            | Public benchmark; 3 homes = generalization test;
                            | millions of events; no license issues.
  3 homes together          | Difficulty gradient: rich (Aruba) → sparse
                            | (Cairo) stress-tests missing-sensor logic.
  5-second windows          | Matches sensor sparsity; localizes behaviour;
                            | no overlap → no leakage.
  Discrete BN               | Categorical data; interpretable CPTs; exact
                            | posteriors; fast enough for real time.
  Hand-designed DAG         | Encodes documented domain assumptions; auditable
                            | (vs. structure learning, which would need far
                            | more data and could return non-interpretable
                            | graphs).
  BDeu smoothing (ESS=5)    | Prevents zero-probability CPT cells in sparse
                            | parent configurations without biasing dense
                            | ones.
  Variable Elimination      | Exact and ~1 ms on 26 nodes; deterministic for a
                            | live dashboard.
  MEU decision layer        | Explicit, auditable safety/disruption trade-off;
                            | graceful under uncertainty; graded responses.
  Asymmetric utilities      | Ignoring hazards costs ≫ nuisance alerts (alarm-
                            | system design standard).
  Weak labels               | Only honest supervision available; rules are
                            | transparent, documented, and reproducible.
  Chronological split       | Prevents temporal leakage; realistic evaluation.
  Rule-based baseline       | Proves the BDN's added value under an identical
                            | utility measure.
  pgmpy                     | Complete, mature, open-source BN toolchain.
  FastAPI + WebSockets      | Async streaming of per-window updates to many
                            | clients; native WS support.
  D3.js                     | Flexible graph rendering for the 26-node DAG.

PART 9 — LIMITATIONS (STATED, NOT HIDDEN)
--------------------------------------------------------------------------------
  1. Weak labels are heuristic proxies, not verified ground truth; metrics
     measure agreement with those rules.
  2. Unusual_Activity is behavioral deviation, NOT security intrusion ground
     truth.
  3. Utility values are project-defined assumptions, not elicited preferences.
  4. Class imbalance (long empty/quiet periods) makes accuracy optimistic;
     macro-F1 is the fairer lens.
  5. CASAS contains no environmental sensors; none were fabricated.
  6. The 5-second window is a design constant; sensitivity to this parameter
     was not swept.
  7. Cairo's ON/OFF door semantics limit the door evidence nodes for that
     home (documented, not converted).
